# 隱私與存儲架構方案（V0.6 評估版）

## 一、現狀：你的數據存在哪裡、誰能訪問

| 平台 | 存什麼 | 訪問者/風險 |
|---|---|---|
| **Supabase Postgres** | 個人信息（基本信息/畫像/元信息表）、匹配、投遞記錄；平台帳號密碼與登錄態為 AES-256-GCM 密文（每用戶獨立 DEK，KEK 存 Render） | Supabase 運維可物理訪問（美企，SOC2）；資料庫僅授權用戶可讀（RLS） |
| **Cloudflare R2** | 簡歷 PDF 等文件 | ⚠️ 目前 bucket 可能為公開讀取（曾用公開 URL）——**這是最大風險點**，任何人拿到鏈接即可下載簡歷 |
| **DeepSeek API** | 簡歷文本、畫像、JD、對話內容（評分/解析/聊天時發送） | LLM 服務商明文接收；應視為「會被看到」 |
| **Render** | 運行環境變量（KEK、DB 密碼、API keys） | Render 運維可訪問；攻擊面標準 |

**總體判斷**：功能上可接受，但有三個可立即改善的風險點：R2 公開桶、LLM 明文輸入、敏感字段（證件號/家庭成員）明文入庫。

## 二、可選方案（按成本/收益排序）

### 方案 A：低成本加固（0.5 天，建議立即做）
1. **R2 改私有桶**：簡歷一律走預簽名 URL（60 分鐘有效），杜絕公開鏈接
2. **LLM 脫敏**：發送 DeepSeek 前對證件號、手機、郵箱做掩碼（如 189****9707）；涉及評分時用「隱私佔位符」替換
3. **敏感字段標記**：元信息表加 `sensitive` 標記（證件號、家庭信息、緊急聯繫人），前端顯示打碼、API 只在投遞上下文按需解密返回

### 方案 B：端到端加密 E2EE（1-2 週，中期）
- 用戶註冊時用密碼派生設備密鑰（PBKDF2/WebCrypto），**個人信息在瀏覽器/擴展內加密後才上傳**，服務器只存密文
- 填報/回傳時在本地解密；RPA 擴展持有密鑰
- 代價：換設備/忘密碼需要恢復機制（備份密鑰片段）；服務器端匹配（貼合度評分）需在**本地解密後再發 LLM**——流程變複雜
- **影響評估**：匹配、自動投遞等核心功能仍可用，但「服務器主動跑任務」（夜間自動投遞）會因密鑰不在服務器而受限——需要用戶設備在線（與 RPA 模式天然契合）

### 方案 C：本地優先 Local-first（2-3 週，長期最優）
- **個人核心信息只存用戶電腦**（瀏覽器 IndexedDB，經 WebCrypto 加密），雲端只存「非敏感元數據 + 加密備份」
- 官方簡歷頁回傳的數據直接進本地庫；填報由擴展從本地讀取——**數據根本不經過我們服務器**
- 代價：換設備需要用戶手動導出/導入加密備份文件；多設備同步難；我們服務器上無法看到用戶資料（對客服/審計有影響）

### 推薦路線（分三階段）
1. **本版本先做方案 A**（R2 私有化 + LLM 脫敏 + 敏感字段標記）——幾乎不影響功能，立刻消除最大風險
2. **V0.7 做方案 B 的「敏感字段子集」**：只對證件號/家庭成員/緊急聯繫人做 E2EE，其餘字段保持雲端（匹配功能不受影響）
3. **V0.8 視用戶規模決定是否全面轉 C**

## 三、回答你的直接問題
- **難度**：A 很小；B 中等（加密/密鑰管理/恢復機制）；C 較大（離線架構 + 多設備）
- **未來用戶影響**：B/C 會讓「換設備」和「夜間全自動投遞」變複雜，但安全性大幅提升；A 無感知
- **是否洩漏風險**：當前 R2 公開桶是實質風險（建議立刻改）；LLM 明文是合規風險（DeepSeek 會看到簡歷內容）；Supabase/Render 為業界標準託管，風險可控
