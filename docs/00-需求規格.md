# 求職簡歷自動投遞系統 — 需求規格書

- 文檔版本：v0.1（草案，待用戶確認）
- 項目代號：JobFly（暫定，可改）
- 形態：多租戶 Web/SaaS 平台（用戶瀏覽器訪問，管理員集中託管）
- 技術決策（已確認）：Python + FastAPI（後端）、React（前端）、Supabase（數據庫/認證/存儲）、Playwright（瀏覽器自動化）
- 自動化底線（已確認）：半自動 + 人工接管；首期投遞範圍：公司官網 / 國際 ATS

## 1. 角色定義

| 角色 | 說明 |
|---|---|
| 求職用戶 | 註冊登錄、上傳資料、配置投遞策略、查看推送與投遞結果、處理人工接管任務 |
| 管理員 | 創建/保管數據庫與項目、用戶審計、平台適配器健康監控、全局配置、投遞成功率報表 |

## 2. 功能需求（FR）— 原始需求映射與驗收標準

### FR-1 用戶管理模塊

| 編號 | 原始需求 | 功能點 | 驗收標準 |
|---|---|---|---|
| FR-1a | 手機/郵箱登錄，只能看自己的數據 | Supabase Auth 郵箱 + 手機號登錄；全部數據表啟用行級安全（RLS），後端強制 user_id 過濾 | 用戶 A 無法通過任何 API 讀到用戶 B 的數據 |
| FR-1b | 上傳簡歷、成績單、簽證等文件 | 文件上傳（PDF/Word/圖片，單文件 ≤50MB 免費層上限），存 Supabase Storage/R2；自動解析出純文本供後續使用 | 上傳成功後可預覽解析出的文本；支持刪除與替換 |
| FR-1c | 簡歷/Cover Letter AI 微調開關 | 兩個獨立開關；開啟後投遞時才允許按 JD 微調；每次微調生成新版本，原始版永不覆蓋 | 開關關閉時投遞一律使用原始文件；微調歷史可回溯 |
| FR-1d | 招聘網站帳號密碼；或指定關注公司 | 平台帳號加密存儲（AES-256-GCM 信封加密）+ 登錄態 Cookie 加密持久化；另支持「關注公司清單」模式（無需平台帳號，直接盯官網/ATS） | 數據庫中查不到明文帳密；登錄態失效自動標記並推送提醒 |
| FR-1e | AI 用戶畫像 + 適合崗位分析 | 簡歷 → LLM 結構化提取（技能/經歷/教育/偏好）→ 生成畫像與「適合崗位 + 貼合度 + 理由」報表，可隨時重新生成 | 生成畫像報表頁面；每項貼合度附可解釋理由 |
| FR-1f | 貼合度閾值 50%–100% | 用戶設置閾值；≥閾值才推送/投遞；硬性條件（學歷/簽證/年限）不滿足時一律過濾並說明 | 閾值可調且即時生效 |
| FR-1g | 全自動/半自動投遞開關 | 三態：關閉（只推送不投遞）/ 達標自動投遞 / 全自動投遞（所有崗位都投，除非無法完成）；無法完成的進人工接管隊列 | 三態行為符合定義，且有明細記錄 |
| FR-1h | 微信/郵箱定時推送 | PushPlus（微信，實名後每日 200 次內免費）、企業微信群機器人（完全免費無日限）、郵箱 SMTP（Brevo 免費約 300 封/天）；用戶可設每日推送時間與渠道 | 按用戶設定的時間準點推送（按用戶時區） |

### FR-2 數據庫

| 編號 | 原始需求 | 功能點 | 驗收標準 |
|---|---|---|---|
| FR-2a | 公開免費數據庫，管理員創建保管，用戶可上傳刪改 | Supabase Free（500MB DB / 1GB Storage / 2 個項目）；附件入對象存儲、DB 只存元數據；管理員通過遷移腳本/後台管理 schema；用戶 CRUD 自己數據 | 管理員一鍵初始化項目；用戶數據上傳/刪改僅限本人 |

### FR-3 主程序

| 編號 | 原始需求 | 功能點 | 驗收標準 |
|---|---|---|---|
| FR-3a1 | 平台登錄同步 | 用戶模塊配置的帳號/關注公司同步至採集與投遞引擎；支持增刪改 | 改配置後下一個採集週期生效 |
| FR-3a2 | 每日定時採集 | 調度器按天合併全部用戶關注目標去重後採集；適配器架構（Workday/Greenhouse/Lever/官網，後續可擴 Boss/獵聘採集） | 每日採集報告：新增崗位數、失效崗位數 |
| FR-3a3 | 每日微信/郵箱推送 | 推送：新匹配崗位（≥閾值）+ 昨日投遞結果 + 待人工處理項 | 每日準時收到，內容含連結 |
| FR-3b | 簡歷自動投遞 | ① 匹配判定 → ② 取最新簡歷版本（按開關決定是否 AI 微調 + 生成 Cover Letter）→ ③ Playwright 打開申請頁 → ④ 結構化字段自動填充（缺失項由 LLM 生成草稿，關鍵字段攔截確認）→ ⑤ 自動上傳簡歷/成績單/簽證等附件 → ⑥ 提交並截圖存證 | 成功提交有外部確認號與截圖；每一步有日誌 |
| FR-3c | 結果告知 + 不明內容補齊 | 投遞成功/失敗即時推送；失敗推送包含原因與「直接框」連結 → 跳轉 H5 頁面填寫 → 程序讀取後在原位置繼續投遞；驗證碼/登錄失效也走同一人工接管通道 | 用戶填寫後 30 分鐘內自動重試投遞 |

## 3. 查漏補缺清單（GAP）與決策

| 編號 | 缺口/風險 | 等級 | 決策 |
|---|---|---|---|
| GAP-1 | 獵聘/Boss 反自動化風控、封號與合規風險 | 高 | 首期只做官網/國際 ATS 全自動；獵聘/Boss 僅採集 + 半自動；全部操作模擬人類行為（隨機延遲、軌跡） |
| GAP-2 | 第三方帳密明文存儲風險 | 高 | AES-256-GCM 信封加密（每用戶 DEK，KEK 存環境變量）；明文永不落庫、不落日誌 |
| GAP-3 | 簡歷缺字段靠 AI 編造 | 高 | 缺失字段生成草稿 + 置信度標記；簽證/學歷等關鍵字段缺失 → 人工確認 |
| GAP-4 | AI 微調簡歷演變成造假 | 中 | 只重組/潤色已有事實；每次微調新版本、記錄 prompt、可回溯 |
| GAP-5 | 重複投遞/漏報 | 中 | 投遞狀態機 + 崗位去重鍵（來源+外部ID）+ 全量審計 |
| GAP-6 | 微信無官方免費推送 API | 中 | PushPlus（實名 200 次/日免費）+ 企業微信機器人 + 郵件；詳見《03-免費服務選型》 |
| GAP-7 | 推送消息內無法直接填表 | 中 | 推送帶連結 → H5 回填頁 → 程序繼續投遞 |
| GAP-8 | 附件入庫撐爆免費額度 | 中 | DB 只存元數據；附件入 R2/Supabase Storage |
| GAP-9 | 單機 cron 不可靠 | 低 | DB 任務隊列 + 冪等 + 重試；分佈式鎖防重複執行 |
| GAP-10 | 缺管理後台 | 低 | 補：用戶審計、適配器健康、成功率報表、配額管理 |
| GAP-11 | 多租戶數據隔離 | 中 | RLS + 後端雙重強制 |
| GAP-12 | 貼合度只靠向量相似度不可解釋 | 低 | 雙層評分：硬性條件逐項核對（不滿足直接過濾）+ LLM 綜合評分附理由 |

## 4. 非功能需求

- **安全**：帳密信封加密；RLS；API 全部 JWT；管理員操作審計日誌；日誌脫敏（不記錄密碼/Cookie 明文）。
- **合規**：《個人信息保護法》— 用戶上傳與代為操作需三份文檔：用戶協議、隱私政策、代投授權書（含第三方帳密存儲與使用的明確告知）。
- **成本**：免費層內運行（Supabase Free + R2 10GB + Render/Railway 免費層 + 保活 cron）；LLM 按量計費是唯一主要變動成本，需記錄 token 用量。
- **可用性**：Supabase Free 無活動 1 週休眠 → 部署保活心跳（每日 ping）；免費層自動化 5 分鐘一次投遞速率限制（防風控 + 防資源耗盡）。

## 5. 範圍外（首期不做）

- 獵聘/Boss 直聘的自動投遞（僅採集 + 人工輔助投遞）
- 打碼平台/驗證碼自動破解
- 桌面客戶端
- 多語言（首期僅簡繁中文 + 英文投遞表單）
